# Protocol discovery (source-verified; Windows smoke test still required)

Resolved baseline SDK in this environment: `mistralai==1.12.4` (unlocked `<2` requirement; repeat the resolution for a real Windows baseline). Source reviewed: `mistralai/extra/realtime/{transcription,connection}.py`, `mistralai/transcriptions.py`, and generated `models` in that version. No credentials or successful cloud capture were available. Do not treat this as permission to ship an untested transport.

- Realtime WebSocket: the SDK joins the configured base URL with `/v1/audio/transcriptions/realtime` and adds query `model=<model>`. Converts `https` to `wss`. Auth comes from SDK security headers (`Authorization: Bearer ...`). It waits for `session.created` before sending `session.update` with `session.audio_format={"encoding":"pcm_s16le","sample_rate":16000}`. Existing app defaults to model `voxtral-mini-transcribe-realtime-2602` and `wss://api.mistral.ai`.
- Each audio frame is a **text** WebSocket message `{"type":"input_audio.append","audio":"<base64 PCM16>"}`. After all audio: `{"type":"input_audio.flush"}`, then `{"type":"input_audio.end"}`. Receive `transcription.text.delta` (`text` field), `transcription.done`, `error`, and session events. Native code includes only bounded parsers and message templates, **not** a network adapter yet.
- The existing warmup generator sends twenty 3,200-byte silence chunks at approximately 50 ms intervals before real microphone audio; it should not appear in the fallback WAV.
- Batch: `POST /v1/audio/transcriptions`, multipart with `model` and `file` (`recording.wav`); the Python caller does not pass language, though the generated SDK supports an optional `language`. Existing batch calls use the default service URL even if a custom realtime base URL is configured. The response's `text` is used. Confirm multipart serializer details, service limits, error schema, proxy behavior, and finalization with sanitized fixtures before implementation.
- The native implementation now sends realtime and batch requests over WinHTTP using this SDK-derived contract. TLS, WinHTTP concurrent send/receive behavior, proxy support, timeout tuning, output timing, and actual provider compatibility still require Windows/API smoke tests before broad publication.
